## Context

The dashboard consumes two data sources:
1. **`data/job_evaluations.json`** — Job evaluation records with fit scores, strengths, gaps, red flags (generated by `/evaluate_jobs_gemini` workflow)
2. **`job_search_tracker.csv`** — Application tracking with applied date, status, company, title (manually maintained by user)

The dashboard must match applied jobs to evaluations by URL and display both sides of the funnel. It must work in a browser without backend services or server infrastructure.

See proposal.md for motivation.

## Interim Artifact

`tools/generate_mockup.py` -> `_brief/mockup.html` is a real, working, kept tool (fixed and verified 2026-09-22 — previously had several hardcoded placeholder KPI values that have since been corrected to compute from live data). It was originally produced as a `powerbi-report-design`-skill mockup/approval step (see `_brief/report-spec.md`) that predates this proposal and was never wired into it. It is **not** this change's target implementation — it's a Python script that bakes current data into a static file at generation time (rerun to refresh), covers only the evaluations side plus the tracker CSV as a flat table, and has no URL-based join between the two (Decision 8 below). This proposal's target is a `fetch()`-based, live-reloading, two-page dashboard with vendor-aware applied-jobs matching, filtering, and export — a materially larger scope.

Relationship going forward: keep `generate_mockup.py` as the cheap interim tool for quick tracking checks (`python tools/generate_mockup.py` then open `_brief/mockup.html`) until this change's fuller design (below) is actually implemented. When implementation of this change starts, decide then whether the Python-generated approach is retired in favor of the `fetch()`-based one, or whether both are kept for different use cases (offline snapshot vs. live view) — not decided here, since implementation hasn't started (0/68 tasks).

## Goals / Non-Goals

**Goals:**
- Provide an interactive multi-page HTML dashboard with two views: Evaluations and Applied Jobs
- **Page 1 (Evaluations)**: Load evaluation JSON, render sortable/filterable job list with key metrics and detail views
- **Page 2 (Applied Jobs)**: Load application tracker CSV, match applied jobs to evaluations by URL, display timeline with evaluation overlays
- Enable users to quickly identify high-fit roles and understand why via detail views and popups
- Support filtering by fit category, date range, and application status
- Allow search and export of evaluated jobs
- Connect application decisions back to evaluation data for post-hoc analysis
- Work offline in a web browser with no backend required

**Non-Goals:**
- Real-time data syncing from external job boards or CMS
- User authentication or multi-user support
- Persistent storage of user preferences (filtering, sorting state) beyond session
- Direct integration with job application tools or CRM systems (CSV link only)
- Analytics or usage tracking
- Mobile app (web-responsive only)

## Decisions

### Decision 1: Single-file HTML application with embedded JavaScript and CSS
**Rationale**: Simplicity and portability. A single `.html` file with embedded JS/CSS requires no build process, server, or deployment. Users can open it directly in a browser.

**Alternatives Considered**:
- React/Vue SPA: Added complexity, build tooling, and dependencies
- Flask/Express backend: Adds server requirement; offline use becomes harder
- Separate JS/CSS files: Requires either server or file:// access issues with CORS

**Decision**: Use vanilla JavaScript with inline CSS for MVP.

### Decision 2: Load JSON data via fetch() with fallback to direct file upload
**Rationale**: `fetch()` works in modern browsers when serving over HTTP/HTTPS. For local file:// URLs, browsers block fetch due to CORS. Fallback: users can paste JSON or upload file via input element.

**Alternatives Considered**:
- Only support HTTP/server delivery: Limits offline use
- Dynamic require or bundler: Adds build complexity
- WebWorker or iframe: Overcomplicates the MVP

**Decision**: Use `fetch('data/job_evaluations.json')` with user-friendly error message offering file upload fallback.

### Decision 3: Real-time client-side filtering and sorting
**Rationale**: No server needed; filtering/sorting is instant and works offline. Data stays in browser memory.

**Alternatives Considered**:
- Backend API with pagination: Adds server, latency, and complexity for small datasets
- Index-based search: Premature optimization

**Decision**: Filter and sort in JavaScript using Array.filter() and Array.sort().

### Decision 4: Color-coded fit indicators (green/yellow/red)
**Rationale**: Enables users to scan the list quickly without reading every score. Aligns with common UX patterns (traffic light).

**Alternatives Considered**:
- Numeric badges only: Less scannable
- Bar charts: Slower to render and more space-consuming

**Decision**: Use CSS background colors for fit category badges and inline score badges.

### Decision 5: Detail panel as modal/side-drawer
**Rationale**: Keeps context visible while drilling into a single job. Easier navigation between adjacent jobs.

**Alternatives Considered**:
- New page/route: Complicates navigation and history
- Inline expansion: Row becomes massive and disrupts list layout

**Decision**: Floating detail panel (right-aligned on desktop, full-width on mobile).

### Decision 6: CSV and JSON export
**Rationale**: CSV for spreadsheet analysis, JSON for re-import or programmatic use. Both respect active filters.

**Alternatives Considered**:
- CSV only: Limits advanced analysis
- No export: Reduces value for external workflows

**Decision**: Provide both CSV and JSON download options.

### Decision 7: Multi-page navigation via tabs
**Rationale**: Single HTML file with tab-based navigation (Evaluations | Applied Jobs) keeps everything portable and offline-capable. Tab switching is instant (no page reloads).

**Alternatives Considered**:
- Separate HTML files: Complicates data sharing and navigation
- Router-based SPA: Adds complexity, requires build tooling
- Single-page with expandable sections: Less clear information hierarchy

**Decision**: Tab-based navigation within single HTML file.

### Decision 8: Job matching via composite key extracted from URL (vendor prefix + canonical job id)
**Rationale**: Raw full-URL string matching is fragile even though URL is the right source field—LinkedIn and Indeed alert links carry per-click tracking parameters (`trackingId`, `jrtk`, etc.) that can differ between the alert email that produced the evaluation and whatever URL is later pasted into the tracker CSV, even for the exact same job posting. Two records in the current `job_evaluations.json` already carry the full tracking query string instead of a clean URL, confirming this isn't hypothetical. Each vendor embeds a stable canonical job id inside the URL, so extracting that id and prefixing it with a vendor tag gives a short, stable join key instead of matching the raw string:
- LinkedIn: numeric id in the path, e.g. `.../jobs/view/4413352108/` → key `LKD4413352108`. Extraction logic already exists server-side (`extract_linkedin_job_id` / `normalize_linkedin_url` in `tools/fetch_inbox.py`); the dashboard re-implements the same regex client-side since it only reads the stored `url` field.
- Indeed: hex token in the `jk` query parameter, e.g. `?jk=a6f9bad38ae0449d` → key `INDa6f9bad38ae0449d`. Not yet canonicalized at ingest time (`fetch_inbox.py` stores the raw href for Indeed), so the dashboard must extract the key at match-time rather than assume a clean stored URL.

Vendor prefixes are an explicit lookup table (`{linkedin: "LKD", indeed: "IND"}`), not derived by slicing the vendor name—"LKD" isn't literally LinkedIn's first three letters, so a derived rule would be inconsistent and risk collisions as more vendors are added.

Glassdoor was considered (a real alert URL keys its job on `jl=`/`jobListingId=`) but is explicitly out of scope: `CLAUDE.md` only directs this project at LinkedIn and Indeed alerts, and `fetch_inbox.py`'s ingestion loop has no Glassdoor branch today, so no Glassdoor URL could reach this dashboard's data regardless of the key design.

**Alternatives Considered**:
- Raw full-URL string match: Rejected—fragile against tracking-parameter drift between email send and CSV entry (see above).
- Title + Company composite key: Fragile (duplicates possible, formatting differences).
- Auto-generated ID: Requires manual ID entry in CSV.

**Decision**: At match time, derive `{vendor_prefix}{canonical_id}` from each record's URL using a per-vendor extractor (LinkedIn: path segment; Indeed: `jk` query param) and join applied jobs to evaluations on that derived key. `job_search_tracker.csv` gains a required `url` column (see `applied-jobs-tracker` spec) so every applied-job row has a URL to extract from. Handle unmatched applied jobs gracefully with an "evaluation not available" state.

### Decision 9: Applied jobs popup with full evaluation overlay
**Rationale**: Clicking an applied job reveals why it was a good match. Users stay in timeline context (don't navigate away), can see strengths/gaps/recommendation inline.

**Alternatives Considered**:
- Hover tooltip (brief): Interrupts workflow, can't show full detail
- Navigate to detail view on Page 1: Loses applied jobs context, page switch overhead

**Decision**: Click → floating popup with full evaluation data. Close popup to return to timeline.

## Risks / Trade-offs

**[Risk: CORS when loading from file://]** → Mitigation: Document the HTTP server requirement for local use; provide file upload fallback for both JSON and CSV. Users can run a simple Python `http.server` or use Live Server extension in VS Code.

**[Risk: Large JSON file performance]** → Mitigation: MVP assumes <1000 jobs. If larger, implement pagination or lazy loading in future iteration. Current design is O(n) filtering—acceptable for typical eval dataset size.

**[Risk: Browser compatibility]** → Mitigation: Use ES6+ (Array methods, fetch, template literals). Target modern browsers (Chrome, Firefox, Safari, Edge from last 2 years). Graceful degradation for older browsers not a goal.

**[Risk: No data validation on import]** → Mitigation: Assume JSON/CSV are well-formed (generated by trusted sources). Add simple error handling for missing required fields. Show warnings if URLs don't match between CSV and JSON.

**[Risk: CSV parsing complexity (quoted fields, commas in data)]** → Mitigation: Use a lightweight CSV parser (PapaParse or similar lightweight lib, or roll simple parser). Handle edge cases: quoted fields, line breaks in data, missing headers.

**[Risk: Unmatched applied jobs (no evaluation record with a matching composite key)]** → Mitigation: Display unmatched jobs in a separate section with notification "Evaluation not yet available" or "Not in evaluation set." Allow manual re-upload of CSV if needed.

**[Trade-off: No persistence of filter/sort state]** → Accepted for MVP. Browser localStorage can be added in future if users request it.

**[Trade-off: Single HTML file grows large with inline CSS and JS]** → Accepted for portability. If file becomes >150KB, refactor into separate files with build tooling.

**[Trade-off: No real-time sync with CSV]** → Accepted for MVP. User must manually re-upload CSV when new applications are added. Could add auto-refresh on-demand button.

## Open Questions

- Should the dashboard support loading data from multiple files (e.g., appending new evaluations to the view)? Defer this—MVP loads a single JSON file.
- Should we pre-populate sample data if JSON fails to load? Defer—rely on error message and file upload fallback.
- What if evaluation data includes new fields in the future? Design supports dynamic field access; no schema breaking changes expected.
